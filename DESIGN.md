# crosscheck, the coding driver: design (v9, built)

The coding driver replaces today's Claude + GPT setup with a full rewrite. It is the daily driver for all of the user's code: Claude writes the code, GPT checks it, and the driver keeps that loop honest with as little friction and as little code as possible.

Status: built in the steps of section 16 (pull requests 1 to 10) and installed on 2026-10-20, replacing the old setup, which was retired the same day (section 11); its repository stays as it is. The code lives in this repository, `shamwi2846/crosscheck-review`.

## 1. Principles (they apply to the driver's own code and to every project it drives)

1. **Simple, easy-to-follow code, everywhere.** Write the simplest solution that does what was asked, so a reader can follow it right away: clear names, small functions, straight flow, no clever tricks, comments only to explain why. Use faster or more complex code only for a measured need (a proven slow loop or query), with a comment saying why. Simplify existing code when you are already changing it, never as a separate rewrite.
2. **Nothing that isn't needed.** No extra options, switches, layers or just-in-case code. This also covers fixes that GPT or Muse suggest. No new library unless it saves real code or real risk; prefer what the language already has, since every added library is code you don't control. "Simplest", not "fewest lines": cramming code to save lines makes it worse.
3. **Removing is improving:** dead code, unused features, and handling of cases whose worst outcome is harmless. First check why the code is there. A removal is reviewed like any change, and removing a safety check from risky code is a risky change.
4. **Rare cases are judged by harm, not by how rare they are.** Keep protection against rare cases that could lose money, lose data or open a security hole (a restart mid-trade, a partial fill, a duplicate order, an order without a stop loss). A simpler check that still protects is fine. Safety checks (input validation, error handling, security checks, guards against data loss) are not complexity to trim. Secrets (keys, passwords, tokens) never go into code or commits; every review checks for them.
5. **Quality means fixing real bugs** that could happen in normal use, not covering every edge case. Effort goes where money, data or security is at stake. An expensive fix never turns a real bug into a gap: look for a simpler fix.
6. **Push back first.** If a request seems harmful or not worth it, Claude explains why briefly, recommends an alternative and waits for the user's choice. This overrides "don't ask" and "never block" for that one decision. Claude makes routine choices itself, and doesn't reopen an objection the user has already weighed.
7. **Fast.** Hooks run on every tool call, so they do almost nothing: no git calls and no scans on edits, one small state file. GPT runs in the background, and follow-ups resume GPT's session.
8. **Fail open, except for safety.** A hook that crashes never blocks the user's work, except the desktop gate (who controls the screen) and the GPT lockdown, which fail closed. Since a failed edit or commit check lets the action through, a hook reads input that starts with a byte-order mark like any other (one such input once failed to parse).

## 2. The workflow it supports

1. **Task.** For a non-trivial request, Claude writes `task.md`: numbered requirements in its own words, with constraints and exclusions. The user's exact words go in a separate local `words.md`, which is never sent to GPT. Claude updates `task.md` only when the user's request changes, never to make a check pass. There is no per-message ceremony. Each session has its own task file, so two sessions in one project never share one. The driver identifies a task by its id and the hash of its Requirements section only: plans, skips and reviews are bound to that hash, so a changed request makes them stale (pre-edit asks again, and a plan gets extended), while edits to the Notes section don't. A running review is voided the same way: a change to the Requirements while it runs acknowledges nothing, and the review runs again. An edit to the Notes doesn't, since GPT never reads them (voiding on any edit once cost a 16-minute paired review, because Claude records progress in the Notes while it waits). Decisions, progress and open items go in Notes, so nothing is lost when the chat is shortened.
2. **Sort each change** by what it does, in any kind of project: no behavior change, normal, or risky. Risky means money and payments, deleting or migrating data, security (logins, permissions, secrets), anything that can't be undone, and in trading code orders, lots, SL/TP, risk, EA inputs and `.set` presets, plus code that risky code uses. Unsure means risky. Order, lot and SL/TP changes are always risky.
3. **Risky: test plan first.** `crosscheck testplan` gets at most 5 cases from GPT, only the realistic ways (rare ones included) to lose money or data or open a security hole that no existing test catches, or for a file none, with GPT's concrete reason. Claude writes each as the smallest test that really catches it. It names every trading or risky file the task expects to touch in one `testplan`, with the existing tests as `--context`, since each plan is a GPT run and Muse's check of it another. A file that isn't risky gets `crosscheck skip --why "..."` instead.
4. **Code.** Claude reads the code it edits itself. Before changing what a function takes, returns or does, it greps the callers, and it fixes a bug once in the shared code rather than in the one caller that showed it. It splits big work into steps of about 300 changed lines or less; each step gets its GPT review and is committed locally, and the whole job is pushed as one pull request once every step is done, so CI runs once per job. It edits with Edit/Write, so the driver sees every change. Steps that depend on a pending GPT result (installs, migrations, releases, trade setup) wait for it, while independent work goes on. Every project the driver works on is a git repository (a one-time `git init`), so a file deleted or moved by a shell command still has its original in git; at session start the driver points out a folder that isn't one, since it tracks no change made there. Tests stay as few as possible: only where a bug could cost money, lose data or break security, plus regression tests for real bugs fixed (step 7). Claude runs the affected tests (and compiles) while working and for follow-up rounds, and the full suite on the final code before the first review and before the commit (an install runs it too), never again on unchanged code. It attaches a short result to the review: the command, the counts and any failures; a prompt carries at most 32 KB of an evidence file, its start and its end. Risky changes need a passing run on the final code.
5. **One review at the end.**
   - **Normal changes:** one GPT at high effort reads the diff with context (with Muse beside it while `muse on`, section 7).
   - **Risky changes:** two GPTs at xhigh read the whole files and the code that calls them. A risky review marks only the risky code as risky (`review --risky --files`; its test-plan tests come along), and GPT rates a file risky only for harm its own change can cause, so docs, config and other changed files reviewed with it stay normal (in one project a paired review rated a `.gitignore` risky next to risky scripts, and its one-line change then took five more GPT runs). Trading files (`.mq5`, `.mqh`, `.set`) are paired by themselves, so `--risky` names only other files whose own change creates the risk; the rule and the usage text both say so, since an EA project once named every changed file, docs and tests included, in all 14 of its paired reviews (305 KB prompts, about 13 minutes each, and a docs-only skip refused).
   - **Comments, formatting or docs only:** a task that touches nothing else may skip GPT, with a recorded reason (`review --skip --why`). Renames and anything else still get reviewed, and the skip is refused for risky files.

   Findings are BUG (it can really happen and cause real harm) or GAP (everything else, recorded in `KNOWN_GAPS.md`).
6. **Follow-ups** check only the open findings and the changed lines. There are at most 3 rounds in total. After that, Claude fixes the remaining bugs, and later rounds look only at the fixed lines, for every kind of change, so nothing ends up unreviewed. A BUG is closed only as fixed (verified) or relabelled a GAP with a reason (in risky code, a one-line proof that it can't happen). Reaching the round limit never relabels anything, and a BUG that is neither fixed nor relabelled keeps the task unfinished.
7. **Finish.** Claude verifies every finding itself, and fixes every BUG with a regression test that would catch it again: an existing or planned test that does counts, one test may cover related BUGs, and a BUG that only records an unmet requirement needs one only when money, data or security depends on it. When it is unsure in trading or money code it fixes; elsewhere it records a gap. Nothing ends with an open BUG or anything unreviewed, and each review chain is closed once nothing in it is open (one chat left 21 finished chains open: status kept listing them, and their bundles were never cleaned up). Claude tells the user briefly what GPT found and what was fixed or left as a gap. Then it commits or opens a pull request.

## 4. Commands

- `review [--files a,b] [--risky] [--full] [--evidence-file out.log]`: the task's one review. Without `--files`, it covers this session's pending changes. Other sessions' changes are reviewed only when named explicitly, and a follow-up is refused while another session has a pending change in one of its chain's files. Shell-made changes are added with `--files`, and the commit guard catches anything left out. With `--risky`, the named files are reviewed as risky, and the session's other changes that come along stay as they are; without `--files`, all of them are. A review can't be split into parallel runs of the same files: `--files` only adds to the session's pending changes. A second run while one is going leaves out, and names, this session's files the first holds (they stay pending until it ends) and reviews the rest; a held file named with `--files` is refused. A review is refused before GPT is asked when a changed file needs a test plan it doesn't have (section 6). A relative path is looked up from the project's root. A path that matches nothing, or matches two different files, is refused before GPT is asked, unless it is a deletion git knows about; so is a link whose real file lies outside the project. A whole-file audit of unchanged code is `review --full` (this happens automatically when nothing changed), not `digest`.
- `review --skip --why "..."`: only for a task that touches nothing but comments, formatting or docs (refused for risky files); the reason is recorded. Like a review, it leaves out this session's files a running review holds (one chat's skip of 38 new research files waited for its own review of 4 others).
- `review --followup <chain> --file response.md`: the next round of a chain.
- `close <chain> --note "F1: gap: <why>; F2: gap: <why>"`: closes a chain. Every open BUG needs a reason: a fix counts once a follow-up resolved it, so a note is only for a BUG left unfixed. A round that leaves its chain with no open BUG and nothing pending says so, with the close command; nothing closes by itself.
- `testplan --files a,b` (the cases are drawn from the session's `task.md`) and `skip --files a --why "..."`. A case that names a requirement id the task doesn't have, or no target file, is refused (one repair), and so is a target with neither a case nor GPT's concrete reason it needs none (`no_case`); that reason is stored as the file's plan and shown to its reviewers.
- `plan --file plan.md [--risky]`: required before leaving plan mode; `plan --skip --why "..."` for a plan too small to matter, or for a revision that only adopts the review's points or narrows scope. A revision that adds new risky scope (money, data, security, an interface, anything irreversible) is reviewed again; the review's result says so, with the skip command.
- `idea --file draft.md`: only for advice on risky or hard-to-undo decisions.
- `digest --files ...|--dir ... --question "..."`: big logs, tester reports, unfamiliar code. The answer has a fixed shape:
  - the answer;
  - evidence, as path:line with the exact quote;
  - counts: passed, failed, and the first failure;
  - scope: what was read, and any truncation;
  - confidence: proven or a hypothesis.
- `research --question "..."`: web lookups, the only mode with web access.
- `write --brief brief.md`: GPT returns a long document's text, the driver saves it as a staged draft, and Claude reads it and applies what is right with Edit. This is never used for code, config or agent files: those are Claude's own.
- `computer --task "..."`: screen control, look and act, never retried.
- `gap [list | <id> --fixed [--real-bug] | --add ...]`. Like a review's or a close's own gap write, its write of `KNOWN_GAPS.md` counts as reviewed when the text it changes was the last reviewed version with no pending change, so no hand edit rides along; otherwise, the next commit asked for a review of crosscheck's own bookkeeping (four chats in two days).
- `lesson --text "..."`: adds a confirmed past mistake to the project's lessons, which every session start prints.
- `status`: pending changes, open BUGs and open chains, in a few lines, and what a commit would be refused for right now, from the commit guard's own check (three chats ran `status`, saw no unreviewed change of their session, and were refused at the commit for shell-made files).
- `on` / `off`: the switch, used only when the user asks.
- `fast on` / `fast off`: Codex's Fast tier for every GPT run crosscheck starts, off until switched on. Codex describes it as 2x speed at higher usage; a short probe measured about 1.3 to 1.4 times faster end to end. `status` and `doctor` show a line while it is on. If Codex ever rejects the tier, each run fails as GPT unavailable with its reason, and `fast off` is the way back.
- `muse on` / `muse off`: Muse Wonder Full (Meta's model, through the user's Muse Code subscription) as reviewer B in every fresh review, normal ones too, and in every risky plan review, and as the checker of every test plan, next to GPT; off until switched on (section 8, Muse runs). `status` shows a line while it is on; `doctor` always says whether Muse Code is installed, and `doctor --live` verifies it while the switch is on.
- `allow-screen --why "..."`: a 30-minute window for Claude's own screen tools (section 9).
- `doctor [--live]`: checks that Codex is found, the hooks are registered and the state can be read, and looks the MQL5 docs server up as a job would, reporting a program or script it names that is missing. `--live` also makes harmless real Codex calls: a read-only run that tries to write a file and must fail, the same check through a resumed session, and the computer lockdown listing (no screen action). It records the Codex version it verified, and warns when Codex has changed since. It runs after install and Codex updates.

Dropped commands (section 13): `task`, `done`, `score`, `run`, `triage`, `stats`, `mql5-compile`, `apply`/`discard`, `mark-reviewed`'s release modes. `allow-claude-cu` becomes the simpler `allow-screen`.

## 5. Hooks

| Hook | What it does | On failure |
|---|---|---|
| SessionStart | Prints the project's lessons, the on/off state, one line of pending work, and a note when the folder isn't a git repository | open |
| PreToolUse Edit/Write/MultiEdit/NotebookEdit | Saves the file's baseline (its content before its first edit since the last review) before the edit happens, because a Write destroys it, and marks the file as changed by this session; then the risk gate (section 6). On the first edit of a file in a session, it also shows that file's open gaps (a plain line scan of `KNOWN_GAPS.md` for the path, nothing more), which Claude fixes only when the change makes them realistic. An edit that then fails only adds an unchanged file to the review, which costs nothing, so no second hook after the edit is needed | open: a file whose original couldn't be saved is reviewed whole |
| PreToolUse Bash/PowerShell | Commit guard: on `git commit` only, one `git status --porcelain` call. The commit is refused if any modified, added or deleted file's current content differs from its last acknowledged reviewed copy (no acknowledgement means unreviewed), so shell-made changes are caught too, or if a BUG is open. The leading folder change is a `cd`, or in PowerShell also `Set-Location`, `sl` or `chdir` (any letter case, with or without `-Path` or `-LiteralPath`; one EA project's chat starts its commands that way), ended by `&&`, `;` or a new line. It or a `-C` may name a Windows path, a Git Bash one (`/c/Users/...`) or a home-folder one (`~/...`): read as a plain Windows path, the last two named a folder that doesn't exist, so eight commits once went through unchecked. A commit must stand alone in its command, after at most a leading `cd`: anything that lets a command line do more than commit (`;`, `&`, `\|`, a line break, a backtick, `$`, `<` or `>`, `--interactive`, a first word other than git, and in PowerShell any parenthesis) is refused, since the check runs before the command, and a new file staged in the same command was still untracked and once went into a commit unchecked. A commit on its own takes only what is already staged, which git status lists, so untracked files stay out of the check. Its own git options or a leading `GIT_` setting that name another repository (`--git-dir`, `--work-tree`, `GIT_DIR`, `GIT_WORK_TREE`) are refused too, since the check doesn't follow them. Reading what else a command stages was tried first and leaked every round (`LC_ALL=C git add`, `git -C. add`, `git add \` over two lines, a heredoc's opening line, PowerShell's `\$(git add ...)`, `-m "$(bash -cm 'git add -A')"`); the rule above is complete by construction, at the cost of a combined command being refused once and split. It's a backstop against Claude slipping, not a lock against someone determined to get past it, so it doesn't parse commit flags or compare staged blobs | open |
| PreToolUse ExitPlanMode | Requires that the plan being presented was reviewed or skipped with a reason (`plan --skip --why`, for a plan too small to matter). The comparison is by hash after whitespace is normalized, so a trailing newline never refuses an exit. The hook uses the plan text from its input, or else the plan file the input names; when neither is there, it allows the exit with a warning | open |
| PreToolUse computer-use tools | Desktop gate: one operator at a time; Claude's own screen tools only inside a 30-minute window opened by `allow-screen` (section 9). Fail-closed needs Claude Code 2.1.295 or newer to honor `"onFailure": "block"`; `doctor` checks this, and without it the screen tools are refused | **closed** |
| Stop | Reminds about unreviewed files (never blocks); blocks while BUG findings are open, but only once in a row, since a stop that follows its own block (Claude Code's `stop_hook_active`) passes, so no prompt hook is needed to count turns | open |

Not carried over:
- **The prompt hook.** The rules already say when to consult GPT, and Stop counts its blocks with `stop_hook_active`.
- **The hook after edits.** The hook before the edit records everything.
- **Shell-edit tracking.** Git covers git projects; elsewhere Claude uses Edit/Write or passes `--files`.
- **Cross-project receipts.**

## 6. Risk

- **Any project:** risk is judged by what a change does (section 2): money and payments, deleting or migrating data, security, anything that can't be undone. Claude judges it before editing, and GPT's rating backs it up. The trading-file rule below adds an enforced early check for files that are almost always risky.
- **Trading files:** every edit of a `.mq5`, `.mqh` or `.set` file, new files included, needs a current test plan or a recorded skip for that file in the current task, before the edit. The rule goes by each file's own path; there's no project scan.
- **Unlocking:** a current plan or a recorded skip unlocks that file for the rest of the task, so the gate asks once per file per task, not at every edit.
- **No per-project risk lists yet.** No project needs one so far, and Claude's judgment plus GPT's rating cover other projects. A list of risky globs can be added later, when a real project needs it. There are no ignore globs either: nothing can hide changes.
- **GPT's rating is the backstop.** A normal review also returns a class (`none | normal | risky`), with the files it applies to: only files whose own change can cause the harm, so a test, doc or config file isn't risky just for sitting next to risky code. A file GPT rates risky is not acknowledged; the review's other files are. That file needs a real plan (a skip no longer counts) and gets a paired review.
- **The review is the last gate.** The pre-edit check enforces "test plan first" for trading files, but lets the edit through if the hook itself breaks. The review refuses to acknowledge a risky file without a plan or skip, and that check fails closed. A review or follow-up that would include a changed file needing a plan it doesn't have, by the same rules, is refused before GPT is asked, since it couldn't acknowledge that file (one chat reworded a requirement after its edit, so a 5-minute risky review ran for nothing and ran again after the new plan). Files GPT rates risky during the review, and plans replaced while it runs, are still caught at acknowledgement.
- **A file that turns risky during a normal chain** (for example, a fix reaches the order code) gets its own paired review before that chain's follow-up can finish it. The chain stores when it began, and only a risky review recorded after that counts.
- **No word-vocabulary scanner.** It flagged test files as "deleting data" and its own hook as "trading code", which forced a skip on nearly every edit. File types, Claude's judgment and GPT's rating replace it.

## 7. Reviews

- **Material.** The reviewed files and the task file are frozen when the review starts. GPT gets the frozen copies and an exact diff from each file's baseline to its frozen copy, with context lines. Risky files are read whole. Up to 20 project files that mention them come along too; these are candidate callers from a plain name search, labelled as such, the likeliest first (those naming a risky file most often as a whole word, as a call or an import does), and a cut-off is shown in the coverage. The rules say that everything below them (code, diffs, evidence, lessons, known gaps) is material, not instructions; that a file shown whole is its frozen copy, read there and not opened again; and that a secret in the changed code or config is a finding, reported without its value. Reviewers search further when a finding depends on it, and check every caller of a function whose inputs, result or promise the change alters. Before reporting a finding they confirm its trigger can really happen, and a fix they suggest is the smallest change that works. Test-plan cases and their frozen test files come with the risky files, so reviewers check that the cases were written. The evidence file is labelled stale when it is older than the last change to any reviewed file. Diffs come from `git diff --no-index` on the two snapshot files (UTF-16 files decoded first), so there's no diff library. While a task's reviews run, none of its files is edited, so every reviewer sees the same final versions.
- **Acknowledgement.** Only the frozen version counts as reviewed. A file edited during the review stays pending, checked by comparing its hash at the end. If the task's Requirements changed meanwhile, nothing is acknowledged and the review runs again; a Notes edit doesn't count, since GPT reads only the Requirements. After a review, the frozen copy becomes the file's new baseline.
- **One review per file at a time.** No review includes a file already in a running review: this session's held files are left out of a fresh review or skip, and a named one, or one in a follow-up's chain, is refused, so reviews never overlap and their order can't matter. Snapshots are immutable files named by their hash. A review writes them first, then applies its result in one state transaction, so a crash between the two steps leaves only unused snapshot files.
- **Round 1 gets the task and the requirements, never Claude's reasoning,** so GPT judges the code on its own.
- **The requirement list** (`task.md`) goes with every review. GPT rates each requirement (MET, PARTIAL or NOT MET, with evidence), and may suggest a requirement the work clearly needs (`possibly_missing`), which Claude decides on. A NOT MET or PARTIAL row is a finding like any other. A follow-up after a requirements change gets the changed requirements and checks them again.
- **Every confirmed finding is reported,** with no cap. The coverage line says honestly what was checked, what doesn't apply (`n/a`) and what wasn't examined.
- **The project's lessons** go into every review prompt, as well as being printed at session start.
- **The open known gaps of the reviewed files** go into every review and follow-up prompt, with their trigger and reason, and GPT reports one again only when the change makes it worse or newly realistic, the task asks to fix it, or there is concrete evidence its reason is wrong, naming its id. Without them, every review of a file found its known gap again (one MarketBell gap was recorded five times).
- **The summary Claude reads** lists the requirements a change doesn't touch on one line, so a long task's rows don't push the findings out of view.
- **The answer is JSON in a fixed shape**: verdict, findings, requirement rows, class and coverage. Codex enforces the shape itself (`--output-schema`, for fresh and resumed runs alike), so the driver only checks the meaning: every requirement id appears exactly once; in a follow-up, every open finding id appears exactly once and no unknown id does; a clean verdict never sits next to a finding or a maintained BUG. If a check fails, GPT gets one repair in the same session, and after that the run counts as not done. No Markdown is parsed, and no model text is ever rewritten. Each finding has: severity, title, location, trigger, harm, failure, fix, test (for high severity) and label (BUG or GAP), plus `reqs` (the requirement ids it shows unmet).
- **The driver shows Claude a short readable rendering**, and logs the full prompt and answer.
- **Chains** live in state: every finding has a stable id (F1, F2, ...), its file and its status. A follow-up lists the open findings by id. GPT answers each one (RESOLVED, MAINTAIN or CONCEDE, with a reason) and may add new findings, but only of MEDIUM severity or above. Lower ones are recorded as gaps. Follow-ups resume GPT's session (fast), with a fresh session if that fails.
- **What a follow-up shows.** Each file's diff since the chain's last round. A file still at the exact snapshot that round froze is named as unchanged, not pasted again: its frozen copy stays listed, and GPT is told to read it whenever a finding, a changed requirement or a caller needs it (the fallback reviewer gets no earlier rounds). Pasting unchanged files again was about 70% of follow-up prompts, and Codex pays for a prompt again on every model call of a resumed session. A changed file with an empty diff (git sees the change as binary) is shown whole.
- **Rounds.** At most 3 full rounds per chain, the first included. After that, rounds look only at the fixed lines, for every kind of change. They report no unrelated findings, but they do report a new bug that a fix itself caused. A rejected fix keeps the task unfinished until its correction passes the same narrow kind of round.
- **Closing a chain** needs one reason per open BUG: either fixed (verified by a follow-up round) or relabelled a GAP with its reason. Hitting the round limit is never a reason, neither in a close note nor in a follow-up's concession (an answer that concedes because of it gets its one repair, like any other wrong answer). Findings closed as fixed are not gaps; relabelled ones go into `KNOWN_GAPS.md` with their reason. The gap entries are written first, and the chain closes after that.
- **`KNOWN_GAPS.md`** is one file at each project's root, written atomically under the project lock. Each entry has an id, a status (open, fixed, or "fixed — was a real bug"), a date, the severity, the task, the place, the problem, the trigger, the fix and the reason it was left. Paths are project-relative, and the home folder and e-mail addresses are removed. Entries are never deleted, only marked fixed. What crosscheck writes there (a review's new GAP entries and entries marked fixed, a close's relabelled BUGs, `gap --add` and `gap --fixed`) counts as reviewed when the text it changes was the last reviewed version with no pending change, so it needs no review of its own; an edit by hand is reviewed like any other change.
- **Pairs** are only for risky reviews, risky plans and the check before a risky release (for an EA: going live):
  - Reviewer A checks the task; reviewer B attacks the risky parts with one short checklist for every project, skipping what doesn't apply:
    - money and trading: duplicate or missing orders, stop losses, lot and margin limits, symbol specs, magic numbers, broker rejects and requotes, partial fills, a restart mid-trade, stale state, rounding;
    - data: partial runs, no rollback, running twice, integrity, the wrong target, deletion without a guard;
    - security: a check missing on some path, secrets in code, logs or errors, comparisons and expiry, injection, unsafe input;
    - general: errors and timeouts, concurrency and stale state, the interfaces between parts.
  - In the cross-check, which belongs to round 1 and doesn't count as a chain round, each one marks the other's findings CONFIRM (with its own harm judgement, BUG or GAP), DISPUTE, SAME AS one of its own, or UNCLEAR (saying what it couldn't check: Muse, whose tools are a sandboxed shell in a throwaway copy, a read-only file tool and the docs lookups, isn't forced to dispute what it still can't see). A DISPUTE must give concrete evidence that the bug can't happen, and Claude checks that evidence. Nothing else happens in round 2. A reviewer whose other side found nothing has nothing to mark, so it runs no cross-check.
  - The merge is deterministic. Agreement and harm are kept apart. Two findings are one only when each reviewer marked the other's as the same as its own; a one-sided SAME AS confirms the other's finding (judged with the label of the marker's own) and folds nothing away, since one reviewer once could merge another's distinct bug into its own and lose it. A finding found by both, or confirmed, is a BUG unless everyone who judged its harm called it a GAP. Disputed means GAP. Unclear keeps the author's label. A merged finding keeps one account, that of a member who called it what it became (then the more severe, then one with a real place over a requirement's "-"), never a mix.
  - A NOT MET requirement rated by only one reviewer follows that reviewer's linked findings: if all of them were disputed, it is a GAP, and the row shows the other reviewer's rating. Otherwise the row shows the worse rating, with MET over NOT IN THIS CHANGE.
  - A completed pair's receipt records the version it certified, so a later round of another chain that rates that very version risky again doesn't escalate it a second time.
  - If either side fails, nothing is recorded ("PAIR INCOMPLETE"), and the pair runs again. When only a GPT reviewer B's first review fails, and not because GPT is unavailable, B runs once more beside A's finished review first, so A's review isn't paid for twice. A paired attempt escalates its risky files when it starts, and only a completed pair clears that, so a failed pair, a killed driver or a retry without `--risky` never counts as one.
- **Muse as reviewer B** (while `muse on`): every fresh review is a pair, GPT A and Muse B, with the same roles, cross-check and merge; risky reviews keep all of a pair's meaning, while a normal review's pair only merges two reviewers' findings (it escalates nothing and leaves no receipt). Muse reads its own version of the prompt, with every frozen copy inline, reads any other project file it needs through crosscheck's read-only file tool, and can run commands (a test, a small experiment, git history) in a throwaway copy of the project inside Muse Code's sandbox (section 8, Muse runs), plus the MQL5 docs lookups where GPT has them. Whether Muse can take part (verified, not cooling down, a clean pre-check) is settled before anything runs, so GPT A never runs twice for a Muse that can't start. When Muse fails in its first review, GPT A's review stands: alone in a normal review, beside a GPT B in a risky one. When it fails in the cross-check, after A marked its findings, the attempt is redone without Muse in fresh sessions. Either way the abandoned turns are renamed out of the `turn-*` files a follow-up's history replays, and the result says "Muse didn't take part" and why. Every file Muse gets, inline or through its file tool, follows one rule: a regular file inside the project once links are followed, git-listed under the name used and its real name, neither name a secrets file's (`.env` and its variants other than examples, private keys, key stores and password vaults, credential files of common tools such as `.npmrc`, `.netrc`, `.pgpass`, `.htpasswd`, `.envrc` and `.git-credentials`, `credentials.*`, and Terraform's variables and state). (Before the file tool, Muse could ask once, in its first review, for up to 20 files it wasn't shown; the file tool replaced that round.) The same rule picks the files a risky plan names and the files a test-plan check gets inline, and material whose size alone shows it can't fit Muse's prompt (more than 3 bytes per character allowed) is never read; candidate callers never include a secrets file, so a `.env` that merely mentions a risky file's name never reaches Muse. Follow-ups stay one GPT, resuming reviewer A. A risky plan review is GPT A and Muse B as well, with the project files the plan names inline (only files git lists, so an ignored `.env` never reaches Muse); when Muse can't take part, a second GPT takes its seat, and the result says why. A test plan GPT designs goes to Muse too: it keeps or drops each of GPT's cases (a drop only to make room for one of its own, with its reason) and adds missed loss paths, within 5 cases; its final plan replaces GPT's only after passing every check of a plan, else GPT's plan stands.
- **Evidence.** Claude attaches its latest test or build output to a review with `--evidence-file` (optional for trivial changes). GPT is always told that the evidence was supplied by Claude and is unverified, and is stale when it's older than the last change. The driver runs no commands itself.
- **When GPT is unavailable** (after one retry), the output starts with `GPT_UNAVAILABLE` and a short handoff: the risky files, the cases and the checklists. Claude runs the `fallback-reviewer` agent on the failed attempt's frozen bundle. The agent answers in the same JSON as GPT, and Claude records it with `review --fallback <bundle> --answer answer.json`. The driver checks that answer with the same validator and applies it in the same state transaction, findings and follow-ups included. It acknowledges only those frozen versions, with the same risk and scope checks, and only if the files still match them. A risky file the failed pair was to read stays escalated (since that pair started), as a file GPT rated risky is: it stays pending, its chain's single follow-ups leave it out, and only its own completed paired review acknowledges it, so one reviewer never counts as the pair. A trading file escalated this way needs a test plan, not a skip, for its next edit. The fallback agent's definition ships with the repository and is installed with it.

## 8. GPT runs (Codex CLI)

- **Effort:**
  - xhigh: test plans, risky reviews and their follow-ups, risky plan reviews, the check before a risky release;
  - medium: `write`;
  - high: everything else.
- **Speed:** every run states Codex's tier, `service_tier="priority"` (Fast) while `fast` is on and `"default"` otherwise, so the user's own Codex config can't make a computer run fast while the switch is off.
- **Isolation for every mode except computer use:**
  - `--ignore-user-config`, a read-only sandbox, and the features `apps`, `plugins`, `multi_agent`, `image_generation`, `tool_suggest`, `computer_use`, `browser_use` and `in_app_browser` switched off;
  - web search off, except in `research`;
  - on MQL5 files only, the read-only MQL5 docs server (`mql5-docs`), with exactly its two lookup tools, `mql5_find` and `mql5_read` (each pre-approved, and the server not required, so a run goes on without it), and its own env settings (such as where its data is). GPT is told to look names up with `mql5_find` first, then read a page with `mql5_read`. Every job on MQL5 code (a review or follow-up, a test plan, and a digest whose material holds a `.mq5` or `.mqh` file, a folder's at any depth) takes it as Codex itself reads its config at that moment (`codex mcp get mql5-docs --json`, fact 24), never a copy: an install-time copy pointed at a folder the docs server's own update had deleted 8 minutes after install, and every MQL5 job ran without docs until a reinstall. A review or follow-up looks it up once, when it freezes its bundle, so all of that attempt's runs (a pair's reviewers and cross-checks, a repair) get the same server, and the note is in its prompt exactly when they do. The docs stay off for anything the driver can't pass on: not enabled, not a stdio server, a working folder, variables taken from Codex's own environment, a value that isn't a string, or an env name that isn't a plain variable name, since each name becomes part of a Codex setting's name. GPT cites the docs page it checked, or marks an API fact "unverified against the MQL5 docs", for example when the server isn't available;
  - the Windows sandbox runs "unelevated".
- **Computer-use lockdown** (computer runs load the user's Codex config, because the runtime needs it):
  - The driver lists what Codex reports as effective, with `codex plugin list --json`, `codex mcp list --json` and `codex features list`.
  - It keeps only computer-use, unified-computer-use, browser and chrome (`@openai-bundled`), plus the `node_repl` and `cua_repl` servers. Those two count only if their program lives in Codex's own runtime folder, so an unrelated server that happens to use one of those names is refused, not trusted.
  - It switches everything else off for that run: app connectors, account plugins (`features.remote_plugin=false`), sub-agents, image generation, tool suggestions, memories and web search.
  - It lists again, and starts only if exactly that is left. Anything it can't establish refuses the run.
  - The user's own Codex config never changes.
- **Timeouts and cancelling:** 20, 30 and 45 minutes for medium, high and xhigh. A timeout, a cancel, or the driver ending normally kills Codex's whole process tree. Only a forced kill of the driver can leave a worker running. For read-only runs that's harmless. For a computer run, the desktop stays owned until every worker has exited (section 9).
- **`write` stays read-only too:** GPT returns the document's text in its answer, and the driver saves it as a staged draft. GPT never writes files.
- **Muse runs** (`muse.js`, reviewer B while `muse on`): Muse gets exactly these tools, named per run with `-c run.toolset=[...]`, and no other: its shell (`powershell`, `powershell_input`) with its own `read_file` and `search` (Meta's servers refuse the shell without those two, fact 26), crosscheck's read-only project-files server, and on MQL5 work the MQL5 docs lookups. No edit, web, memory, scheduling, workflow or sub-agent tool. (The user chose to give Muse commands on 2026-10-30, accepting that they can read anything on the PC, logins included, and that Meta sees it.)
  - **The shell** runs only inside Muse Code's own sandbox, with the network as restricted as Muse allows (`--sandbox-network restricted`; never `--yolo`, `--disable-sandbox` or `--disable-approval`), as the sandbox's own user, in a throwaway copy of the project. The copy is a clone of the project's history cut off from it: no remote, and `--no-hardlinks --dissociate`, since the sandbox lets Muse write the copy's git storage. It sits at the project's HEAD, with the change under review written in from the frozen copies (and its deletions made); for a risky plan's review, a plan file that lies in the project is written in as the text under review. It is made afresh before every Muse run, a retry and a cross-check included, so no run sees what an earlier run's commands changed. It is made by git with no system or user configuration, no `GIT_*` variable of crosscheck's own environment and an empty template, so no hook, filter or fsmonitor of the user's runs, and a reviewed file is written in only where no folder on its way is a link, over its old entry, never through it. It is removed when the job ends (a removal that fails is reported, never left silently). The commands' temp folder is `.crosscheck-tmp` inside the copy (Muse's TEMP and TMP): the sandbox opens the temp roots those name, and its user can't write a folder of the user's anywhere else, so the user's real temp stays closed. A link at that name stops the run. Git is told the copy is a safe directory, since its owner isn't the sandbox's user. So the commands can write only inside the copy (and Muse's own sandbox folder) and reach no network; reads stay open.
  - **crosscheck's servers** are attached per run with `-c mcpServers.<name>=<json>`: the read-only project-files server (`muse-files.js`, started by its absolute installed path with the absolute path of a manifest in the attempt's bundle), and on MQL5 work the MQL5 docs server GPT has (each of its env values reaches it only through a `CROSSCHECK_MQL5_DOCS_<NAME>` variable set for that Muse process, since Muse takes env values only as a whole `${VAR}`). A named tool whose server can't start makes Muse refuse the run, so a docs server that can't start keeps Muse out (the echo pre-check fails, says so, and takes nothing away: a failed echo run made no model call and ran nothing), where GPT goes on without docs. The file server's three tools (`list_files`, `read_file`, `search`) read only what every file Muse gets may be (inside the project once links are followed, git-listed under both names, no secrets file), a reviewed file only as its frozen copy and the plan under review never again; every answer is cut at 100,000 characters, a search stops after 20 MB, the answers of one manifest stop at 2,000,000 characters in all (counted from its log, so a resumed Muse can't start again), and every answer is logged whole in the bundle before it goes back.
  - **Running it.** Contributor mode is on: the user chose to let Meta train on their code (2026-10-30). It runs the verified Muse program directly, never the self-updating launcher, and only the version `doctor --live` verified, in the job's copy of the project (untrusted in Muse, so no project rules load; a resumed session works in the same place, made afresh). A run that streams blank output 300 times in a row is stopped as a loop. Muse's usage or login failures start a cooldown for Muse alone. Its prompt says which tools it has, what the copy holds and that nothing it changes there is kept, and carries GPT's docs note exactly when it has the docs.
  - **The check.** Muse's own record of each session (`export`) is checked before the session's first real run (an echo run, which makes no model call, with the same tools and flags) and after every run: exactly the tools that run was given, matched by their full names; the sandbox it was asked for (its permission record says the files are "managed" and the network "restricted", and its security note "Shell sandbox: on."); only the eight context messages a clean shell run has (among them `memory_snapshot`, Muse's memory notes, which can't be turned off: the user accepted that); only the skills verified with the program; and every tool call that started listed with its arguments. Anything unsafe discards the answer and the verification, the pre-check's included; a run without its tools only loses its answer. A failed run's session is checked too, before any retry, and one that left no readable record counts as unsafe: even a run Meta refuses leaves one, so its commands couldn't be seen (a usage or login failure still starts the cooldown, so `doctor --live` makes no model call meanwhile).
  - **The log.** Every call and every result the record shows (the tool and its arguments; a command's exit code and output) is kept in the job's bundle, one file per run (`muse-calls-<session>-<n>.jsonl`, since a resumed session's record holds its earlier runs too), failed runs included. A run whose calls can't be written there loses its answer.
  - **`doctor --live`** runs Muse exactly as a review does, shell and sandbox included (in a scratch folder, without the file tool: it has no project), and has its shell try a write outside that folder (the path as a PowerShell literal, whatever the temp folder is called). It passes only when the log shows that very command denied (an exit code and PowerShell's PermissionDenied error: a Muse that never tried, a parse error or a shell that never ran proves nothing), the file doesn't exist and the session check passes.
- **Usage limits:** a limit or login error starts a 15-minute cooldown and the fallback path. No new GPT runs start during the cooldown. The message "model is not supported when using Codex with a ChatGPT account" means the usage ran out; it is not a bug.
## 9. Computer use

- Claude avoids the screen: files, logs, CLI tools and APIs come first (for MT5: `MQL5/Logs`, the terminal logs, tester reports, exports and `.set`/`.ini` files, read directly). Screen control is delegated to GPT with `crosscheck computer`.
- **One operator at a time across all projects.** One global ownership record, under one global lock, is checked and taken in one step. It names the operator. For a GPT run, that's its driver and Codex worker processes (noted at Codex's first output and every 2 seconds after), and it stays held while either is alive, so a worker that outlives its driver still owns the desktop. For Claude, ownership is the `allow-screen` window itself: 30 minutes, bound to the session id, released when it expires or on `off`. A hook can't tell whether a Claude session is alive, so there's no liveness check, and another Claude session is refused during the window. A second GPT computer run gets BUSY, and Claude's own screen tools are refused while GPT holds the desktop.
- **Claude's own screen tools** are for when delegating is clearly worse, for example an app GPT isn't approved to capture. `allow-screen --why "..."` opens a 30-minute window and records the reason.
- A computer run is never retried, because repeating clicks is unsafe. Files that change during the run are reported (git status before and after).
- Neither model trades, moves money or enters credentials.
- Known limits:
  - In background runs, Codex's own per-app approval refuses screenshots of apps the user hasn't approved in the Codex app.
  - Codex's sub-agent tools stay visible even with `features.multi_agent` off. They run under the same lockdown, and `doctor --live` reports what a computer run can actually reach.

```
~/.claude/crosscheck/  the installed copy (what the hooks run): code only, replaced by installs
~/.claude/crosscheck-state/   live state, never touched by install

                   so every worktree of a repository shares them)
<project>/KNOWN_GAPS.md
```

- **The shared records in `global.json`** (hooks read them; the CLI writes them, each under the global lock):
  - `off`: true while the user has switched the driver off;
  - `fast`: true while Codex's Fast tier is on (`fast on` / `fast off`);
  - `plans`: `{ <hash>: { at, skip? } }`, a reviewed or skipped plan by the hash of its text with every run of whitespace made one space (`planHash` in `hook.js`, shared with the `plan` command);
  - `sessions`: `{ <session id>: { roots, at } }`, the projects a session edited (Stop checks them all);
  - `desktop`: `{ pid, workers, project, at }`, the computer run that owns the desktop: its driver and every Codex worker process it noted, written as they are noted;
  - `screen`: `{ session, until, why }`, Claude's allow-screen window (`until` in milliseconds since 1970);
  - `cooldownUntil`, `cooldownReason`: the usage cooldown.
- **Atomic writes, one lock.** Every state write goes to a temporary file and is renamed into place, under one lock file per project. An unreadable state is never overwritten: the driver reports it and refuses to acknowledge anything.
- **A hook that fails open is never silent.** It writes the error to a hooks log, and `status` and `doctor` show it.
- **Log cleanup.** Logs older than 30 days are deleted, unless they belong to an open chain.
- **A project is its git repository:** its identity and root are the repository's top folder, wherever Claude Code was started inside it.
- **The session** is identified by `CLAUDE_CODE_SESSION_ID`, which Claude Code sets for hooks and for its shell commands. Without it, in the user's own terminal, session-scoped commands refuse unless `--files` names the files.
- **A GPT run whose driver died,** for example when the session closed during a background review, applies nothing. Its running-job record has a dead process, so `status` shows it as not done, and the next start clears it.
- **Paths.** Paths with spaces and non-ASCII letters must work everywhere, because the user's folders have both. Processes are spawned without a shell.

## 11. Install and update

- **Prerequisites:**
  - Node 22 or newer;
  - the Codex CLI, logged in;
  - Claude Code 2.1.295 or newer;
  - git.

  `install.js` checks them all first. It shows what it will change in settings.json and CLAUDE.md, and asks before changing anything. After install, Claude Code is restarted (a new terminal or app session).
- **Install.** `node install.js` runs the tests, copies `src/` and the fallback agent into place, writes `RULES.md`, and registers the hooks in `~/.claude/settings.json`. Registering replaces every hook entry of an earlier driver install and keeps every other hook.
- **Config changes made meanwhile stay.** Right before writing, install reads config.json again under its lock, which it holds until everything is written: a value changed while it asked (a verification doctor took away, a path set by hand) is kept, and an unreadable config.json stops the install with nothing written.
- **Simple order.** Each install waits until no GPT job is running, copies the code, writes RULES.md and CLAUDE.md, and writes settings.json last, by atomic rename. Writing settings.json is the switch itself, so a failure before that changes nothing that's in use.
- **Personal details stay out of the repository.** The user's `~/.claude/CLAUDE.md` becomes a short personal file that imports the rules (`@~/.claude/crosscheck/RULES.md`) and holds the personal lines: the MT5 standing confirmation for the user's own PC (named there, not here), and anything else that belongs only to this user. The public repository never holds secrets, account numbers or EA code. An install keeps a CLAUDE.md whose first line is already the import line exactly as it is, so personal lines changed there (by the user or another session) are never reverted; only a CLAUDE.md without that line is written from `crosscheck-state/personal.md`.
- **Update:** `git pull`, then `node install.js`. Going back to an earlier driver version is `git checkout <version>`, then `node install.js`.
- **The old setup is retired** (2026-10-20): `install.js --restore` and the first install's backup that it put back are gone, and the installer no longer knows the old setup's hooks or state. Switching crosscheck off is `crosscheck off`.
- **No more release or backup machinery.** The repository is the release.

## 12. Tests (only what protects real harm)

The tests use Node's built-in runner (`node --test`), an isolated temporary home folder, and a Codex stub that returns canned JSON. They cover:

1. GPT isolation: the exact Codex arguments per mode; research is the only mode with web access; `write` stays read-only.
2. Computer lockdown: one success, plus a refusal for each of these: a listing that fails, unreadable output, a name that can't be switched off, something left enabled, and a look-alike `node_repl` from outside Codex's folder.
3. Risk gate: a trading file without a plan is refused; a skip unlocks it; a GPT escalation can't be skipped; a changed task makes an old skip stale.
4. Baselines and acknowledgement: a Write over a file with uncommitted changes keeps its original; only the frozen version counts; a file edited during the review stays pending; changed requirements acknowledge nothing, and a Notes edit doesn't stop the acknowledgement; a review that includes a file already under review is refused.
5. Findings: an open BUG blocks Stop, but only once in a row; a GAP never blocks; closing a chain needs a reason per BUG, and the round limit is no reason.
6. Answers: missing or duplicate requirement ids, an unknown follow-up id, and a clean verdict next to a maintained BUG are each refused.
7. Pair merge: both found it, both labelled it GAP (it stays a GAP), confirmed, disputed, a NOT MET row linked to disputed findings, and a failed side recording nothing.
8. Follow-ups: ids, the round limit, rounds limited to fixed lines after it, and a file that turns risky mid-chain.
9. Commit guard: a commit while a tracked change is unreviewed, or a BUG is open, is refused.
10. Desktop gate: two projects compete for the desktop; a dead driver with a live worker keeps the desktop; Claude's screen tools work only inside an `allow-screen` window; the hook fails closed.
11. Plan gate: a plan changed after its review is refused, and a skipped one with a reason passes.
12. Fallback: an edit after the fallback review isn't acknowledged by it.
13. Atomic state: an unreadable state file is never overwritten.
14. Fixed-lines rounds: a regression caused by a fix is reported, and the task stays unfinished.
15. Install in an isolated profile: unrelated hooks are kept, an earlier install's hooks are replaced, and state is untouched.
16. Session scope: a review never acknowledges another session's changes unless they are named.
17. Review skip: refused when any file is risky, and recorded with its reason when it is allowed.

Each real bug found later gets a regression test that would catch it again (an existing one that does counts), and there are no tests for anything else.

## 13. What the old setup had that the rewrite drops, and why

- **The requirement-list ceremony** (task --start, --update or --same after every message, words-file rules, strict requirements text block): replaced by `task.md`, updated only when the request changes, plus JSON requirement rows in the review.
- **The `done` check:** the final review already checks every requirement against the code, so done added a slow GPT run that mostly flagged items outside the task.
- **`score`:** a review with the rubric in `task.md` does the same.
- **`run` and its evidence records, and `triage`:** never used. Claude runs tests itself and passes the output.
- **`mql5-compile`:** the mql5-coding skill compiles (`Compile-Mql5.ps1`).
- **Paired runs for ideas, test plans and investigations:** the rules never pair them.
- **The word-vocabulary risk scanner:** too noisy (section 6).
- **Shell-change tracking, discovery windows, cross-project receipts:** Edit/Write tracking, `--files`, git (every project is a repository) and the commit guard cover them.
- **Ignore globs:** with no shell tracking there is nothing generated to ignore, and an ignore list could hide changes.
- **Cut after Fable's review** (not worth their code):
  - content-matching and flag parsing in the commit guard (it only has to catch Claude slipping);
  - review ordering by freeze time (one review per file at a time removes the problem);
  - install staging and automatic rollback, and two restore modes (git already keeps the versions);
  - per-project risk lists (no project needs one yet);
  - the 2-minute desktop window.
- **Re-checking a review when a file it depends on changes later:** the rule "no edits while a task's reviews run" covers it without machinery.
- **Markdown answer parsing,** with its decoration-blind readers and line grammars: one JSON schema replaces all of it.
- **Replaying finding ids from logs:** ids live in state.
- **Release, backup, manifest and mirror machinery:** the repository is the release.
- **`stats`, `apply`/`discard`, the prompt-hook reminders, the hook after edits, the duplicate-review check (one review per file at a time covers it), legacy chain formats:** not needed. `allow-claude-cu` becomes the simpler `allow-screen`.

## 14. Facts learned the hard way (carried over, so nothing has to be rediscovered)

1. Codex's sandbox covers shell commands, not MCP tools. Isolation needs `--ignore-user-config` and the feature switches. `--ignore-user-config` alone still exposed about 1,100 app connector tools.
2. `-c mcp_servers.<missing>.enabled=false` makes Codex refuse to start ("invalid transport"): only switch off servers that are listed.
3. A single plugin's switch works only unquoted (`-c plugins.<id>.enabled=false`) and only for plugins installed on this PC. The plugins on the ChatGPT account go only with `features.remote_plugin=false`. `features.plugins=false` also removes `cua_repl`, which breaks computer use.
4. `codex plugin list --json`, `codex mcp list --json` and `codex features list` honor `-c` and report the effective state.
5. Follow-ups resume with `codex exec resume <session id>`. Resume has no `-s` or `-C` flag, so the sandbox is set through config there.
6. Model answers: one strict machine block with one repair beats any attempt to read decorated text. Never rewrite model text.
7. Language modeling in a risk check (comment exemptions, statement windows) drew new high-severity findings in every round. Keep risk rules simple and file-level.
8. Test plans: at most 5 cases, no variants. Chasing coverage produced about 10 times more test code than real code. A missing test without real harm is a gap. A plan asks only for protection no existing test gives, and may have no case for a file, with GPT's reason, which the reviewers check: in the first four days of use GPT filled 4 or 5 cases in most plans, and the rules asked for a new test for each of 107 fixed bugs, an unmet requirement included.
9. Never edit the driver's files while its tests run. Test the installed copy against a copy, or run the tests before installing.
10. Hide secrets when reading config files, including keys inside URLs. GPT may later read the transcript.
11. A running Claude desktop app writes its in-memory settings back over its config file. Edit that file, then restart the app.
12. Windows: paths with spaces and non-ASCII letters, UTF-16 files, process trees (Codex starts children, and killing the parent alone leaves them running), and the slow `npm root -g` (find Codex once and store the path).
13. A risky-review receipt counts only for the files the reviewers read whole. A chain's start time must be exact: whole-second log stamps let a same-second review pass as later.
14. GitHub: never `--admin`, never force-push. A PR is done, and merged, when GitHub's CI checks pass on its final head commit and it merges cleanly.
15. Claude Code honors a hook's `"onFailure": "block"` only from version 2.1.295; older versions run a crashed hook as "allow".
16. `codex exec --output-schema <file>` (and `codex exec resume --output-schema`) makes GPT's final answer follow a JSON Schema. `doctor --live` checks that it is enforced on the installed version.
17. Claude Code passes a Stop hook `stop_hook_active` when Claude is continuing because of that same hook's block. That is enough to block only once in a row.
18. Test stubs record what they were sent and return canned answers. They never model an external tool's behavior (a stub that imitated GitHub's API drew new findings every round). The real tool is checked once, live and read-only (`doctor --live`).
19. In PowerShell, `git commit -F -` with a here-string doesn't read stdin. Write the message to a file and use `-F <file>`.
20. A relative path must be resolved from the project's root, not the shell's current folder (it once pointed reviews at the wrong project). An ambiguous or missing path stops the call.
21. Writing `KNOWN_GAPS.md` in place, or closing a chain before its gap entries are saved, could lose entries. Write atomically, and record the gaps before closing.
22. Codex attaches the user's instructions file in `$CODEX_HOME` (`AGENTS.md`, or `AGENTS.override.md` when there is one) to every run, isolated ones included: `--ignore-user-config` doesn't keep it out (its help says it skips `$CODEX_HOME/config.toml`). `-c project_doc_max_bytes=0` doesn't stop it either (that covers a project's own files), and `-c instructions=""` must never be used: it keeps AGENTS.md and replaces Codex's own base instructions instead (21,835 characters became 42, measured on Codex 0.162.1). The user's file holds only the MT5 test-PC block, so reviews keep it.
23. When GPT answers "429 Too Many Requests", Codex retries the stream ("Reconnecting... n/m (exceeded retry limit, last status: 429 Too Many Requests)") up to its provider's `stream_max_retries`, and each try can wait up to `stream_idle_timeout_ms` (5 minutes by default), then exits on its own (Codex 0.162.1). One run waited this way until crosscheck's 30-minute timeout while about nine research jobs and other chats' reviews ran. The timeout stays: stopping on the first 429 would kill runs that recover, and a shorter idle timeout could cut off long silent reasoning. Running fewer jobs is no cure either, since the limit is shared by every chat on the account.
24. `codex mcp get <name> --json` prints a server's entry as Codex reads it from its config: `name`, `enabled`, `transport` (`type`, `command`, `args`, `env`, `env_vars`, `cwd`), the tool lists and the timeouts (Codex 0.162.1). A hand-made TOML reader for the docs server missed valid spellings (spaces around a header's dots, a comment after a header, a quoted key) and dropped settings each time, so crosscheck takes Codex's own reading. It takes about 160 ms, so each MQL5 job asks again. Settings reach a run through `-c mcp_servers.mql5-docs.env.NAME="value"`; a probe run got its docs answers that way. The docs server updates itself into a new versioned folder and deletes the old one (0.1.4 to 0.1.5 on 2026-10-26), and Codex's config follows it.
25. Muse Code 1.4.14 (2026-10-30): the model id is `muse-wonder-full-1.0` (`model-profile show` accepts any name, so it proves nothing). `muse exec --json` prints `{ payload_type, payload }` lines; the answer is the `run.terminal.*` event's `text`. With `--disable-write --disable-shell` it still keeps 18 tools, among them memory reading, scheduling and workflows; neither `-c` nor a custom preset's `excluded_tool_names` removes any (both were accepted and ignored), and `skills.activation.*` settings change nothing either. Only `--preset empty` leaves none. A project Muse trusts lets it start sub-agents, so the workspace is an empty folder; it can read files by absolute path from there. `--output-schema` holds, but once in six runs Muse wrote its answer and then streamed blank lines without end. `--provider echo` sets a session up without a model call, and `export --session <id>` shows the tools and context a run really had. The launcher updates itself, the program `muse-bin-<version>.exe` runs directly. With `--preset empty`, `-c mcpServers.<name>=<json>` (one server per `-c`; the whole `mcpServers` map is refused; `command`, `args`, `env`, `mode` "required" or "optional") attaches a stdio MCP server, and the session's record then shows exactly that server's tools as `mcp__<name, - as _>__<tool>`, with the same six context messages; two servers together work. An env value must be a whole `${VAR}` naming a variable set in Muse's own environment, or the run is refused. An optional server that can't start leaves the run going without its tools. A real run called an attached server's tools headless under `--approval-mode never`. `--contributor-mode on` is accepted and adds no context message. MCP over stdio is newline-delimited JSON-RPC (initialize, tools/list, tools/call); a server of about 20 lines answered it.
26. Muse Code 1.4.14's shell (2026-10-30, real runs). `--preset empty` drops the shell with every other native tool, and a named toolset can't add it back; without the preset, `-c run.toolset=[...]` gives a run exactly the tools it names, native and MCP alike. A named-toolset run adds the context messages `sandbox_policy` and `memory_snapshot` (`memory={...}` settings are accepted and ignored, so it can't be turned off); the skills stay Muse's bundled and plugin ones. The sandbox (`muse sandbox windows check`: backend windows_elevated, ready) runs commands as its own user (`muse-sbx-r1`) in PowerShell's constrained language mode. Reads work anywhere. Writes work only under the workspace, Muse's own runtime temp folder (`AppData\LocalLow\muse-shell-sandbox-<id>`), the active repository's git storage and the temp roots named by Muse's TEMP and TMP: pointed inside the workspace, writes to the user's real temp, `C:\Windows\Temp`, `AppData\Roaming`, the crosscheck state and another repository's `.git` were all denied; pointed at a folder beside the workspace, even that folder wasn't writable. ## 15. The rules Claude follows (draft of `RULES.md`, imported by the personal CLAUDE.md)

The rules say *what* to do; the driver handles *how*, so no command flags or hook details appear here. Target: 60 to 80 lines, against about 140 today.

- **Priority when rules conflict:** first, the safety of money, data and security; then the user's explicit instruction; then quality (real bugs fixed); then speed; then token cost.
- **Talking to the user:**
  - the answer or decision first, then the reason;
  - short replies in plain English, and a technical term explained the first time;
  - no internal ids, file paths, logs or long lists unless asked;
  - nothing reported while working (no steps, review details or reasoning), except a decision the user must make or a few words when the app asks for a status; at the end, one short conclusion, with detail only when asked;
  - when Claude must ask, one question at a time, with a recommendation;
  - Claude pushes back first (section 1, principle 6).
- **Roles and ground rules:**
  - Claude writes all code. GPT reviews, plans, reads large material and operates the screen, always read-only and isolated.
  - Claude never changes its own effort level or its settings.
  - Code is edited with Edit/Write, so the driver sees it.
  - Neither model trades, moves money or enters credentials.
  - Writing is not sending: no email, publishing or new repository without the user's OK. The standing approvals are: complete, reviewed work is pushed as a PR with auto-fix on, and a PR is merged when it's green.
  - The driver is switched off only when the user asks.
- **Code:** section 1, principles 1 to 5, word for word.
- **Facts first:** when an external tool's behavior matters and is uncertain, Claude checks its docs and runs small experiments before designing, and records the facts in the task notes.
- **A task:** section 2, word for word. One exception to "every code change gets reviewed": a task that only touches comments, formatting or docs may skip GPT with a recorded reason. Renames and anything else still get reviewed, and risky files never skip.
- **Recurring confirmed mistakes** go into the project's lessons.
- **Findings:**
  - BUG means it can really happen and cause real harm. In risky code (money, data, security, trading), an unlikely trigger with a big possible loss is a BUG too, such as duplicate orders, an order without a stop loss, a migration that loses rows, or a leaked key.
  - GAP means everything else, recorded with its severity.
  - Claude makes the final call. In risky code, a BUG becomes a GAP only with a one-line proof that it can't happen. Closing a review chain or hitting the round limit never turns an unfixed BUG into a gap by itself.
  - Paired reviews: each reviewer marks the other's findings (when the other found any); two findings are one only when both say so. A finding both found, or confirmed, is a BUG unless everyone who judged its harm called it harmless; shown impossible means GAP; unclear keeps the author's label (an unclear BUG stays a BUG).
  - Claude fixes an existing gap only when the current change makes it realistic.
  - A missing or weak test is rated by its real harm, not by the test case's rating.
  - When Claude is unsure whether a finding is real, it fixes the finding in trading or money code and records a gap elsewhere.
- **When GPT is needed:**
  - every code change, through the task's one review (the exception is under "A task");
  - plans before leaving plan mode, and substantial plans written in chat; a plan too small to matter is skipped with a reason, and so is a revision that only adopts the review's points or narrows scope (one that adds new risky scope is reviewed again);
  - an idea check, only for advice on risky or hard-to-undo decisions;
  - big reading jobs (logs, tester reports, unfamiliar code), web lookups, long documents and screen control.

  GPT is not needed for questions of fact or advice that isn't risky.
- **Background:** GPT runs in the background. Claude never polls; it works on something else, never on the files under review, or ends the turn while it waits. Many GPT jobs may run at once: nine research jobs at a time worked, and the limit is shared by every chat on the account. A job that fails with "too many requests" is retried once the running ones finish (fact 23).
- **If GPT is unavailable:** the fallback reviewer takes over (section 7), and Claude tells the user.
- **Computer use:** section 9.
- **Pull requests:** push only complete, reviewed work, never with `--admin` and never force-pushed. A PR is done, and merged, when GitHub's CI checks pass on its final head commit and it merges cleanly.
- **Several coding jobs:** one per project at a time, since PRs merge on green CI unread and two each-green PRs can break main together; research and design jobs may run alongside. Coding jobs run only in local chats (crosscheck isn't installed in the cloud). A handoff shows the user its project, starting commit, PR name and note; starts from GitHub's main, verified; and carries the whole task file. A job's copy is deleted only after the merge and with nothing unsaved.
- **Documents:** long documents are drafted by GPT and reviewed by Claude; short texts Claude writes itself.

The personal `~/.claude/CLAUDE.md` holds only what belongs to this user and this PC: the import line, and the MT5 standing confirmation for the user's own PC, named only in that file (run tester smoke tests without asking on that PC only; ask on any other PC or for a real-money account).
